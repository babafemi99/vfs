# Decisions

These are choices made where `lab/docs/README (1).md` was ambiguous, or where we cut scope.

## Scope and phases
- **Backend only for now.** The web UI, SSE, Docker Compose and the end-to-end script come later.
- **No treasury.** Reconciliation is optional; we build it only if time allows after the lifecycle works.
- **No chaos testing.** We assume brokersim is reliable. Lifecycle tests drive it through its JSON `/dev` API. The one case brokersim can't produce (a 500 after it created the order) uses an `httptest` fake.
- **Phases:**
  1. Money core.
  2. Workers, outbox with backoff and dead-letter queue (DLQ), and placing orders.
  3. Webhook inbox, fills, cancel and the stuck-order sweeper.
  4. Reconciliation (optional).

## Layout and environment
- **Folder:** `tradeapp/` at the repo root, its own module `github.com/babafem99/vfs/tradeapp`.
- **Postgres:** local Postgres 18 with no password. App database `tradeapp`, test database `tradeapp_test`. We'll add Docker Compose only if we need something we can't install locally.
- **Dependencies:** pgx v5 is the only Go dependency.

## Layers
Dependencies point one way: transport → service → repository → domain.

### domain
Models (account, ledger entry, position, order, quote, fill, activity), business errors, and pure rules with no I/O:
- Entry validation.
- Position maths: `Hold`, `Release`, `ApplyBuy`, `ApplySell`.
- Order statuses.
- Money formatting.

### repository
Dumb data access:
- **`Repository`** holds the pool and has `RunInTx`, which commits on success and rolls back on error or panic.
- **Each repo** (`LedgerRepo`, `PositionRepo`, `OrderRepo`, `QuoteRepo`, `ActivityRepo`, `IdempotencyRepo`, `InvariantRepo`) is a struct with no fields.
- **Every method:**
  - takes `(ctx, tx pgx.Tx, …)`;
  - runs one SQL statement with explicit columns and an explicit `Scan`;
  - holds no logic.
- **Return values:** writes return `error`; reads return data and `error`.
- **Errors:**
  - No row found → `domain.ErrNotFound`.
  - An `ON CONFLICT DO NOTHING` insert that hits an existing row → `domain.ErrDuplicate`.
- **No arithmetic in SQL.** For example, `UpdateAccountBalance` sets the new balance, and the service computes it.

### service
Validation, ID generation (prefixed ULIDs from `pkg/lid`) and orchestration:
- **Use cases:** each exported method (`FundAccount`, `GetAccount`, `ListActivity`, `CheckInvariants`) is one use case and opens one `RunInTx`.
- **Building blocks:** unexported helpers that take a `pgx.Tx` (`postEntry`, `holdCash`, `releaseCash`, `payBuyFill`, `creditSellFill`, `holdShares`, `applyBuyFill`, …) run inside the caller's transaction, so a use case can combine them atomically.
- **No idempotency:** the service knows nothing about idempotency keys.

### transport (`internal/transport/http`, package `httpapi`)
- Decodes requests, calls the service and encodes responses.
- Maps domain errors to HTTP errors.
- Owns request idempotency (see below).

## Transactions
- **Isolation: Read Committed, not Serializable.**
  - Money is protected by row locks (`SELECT … FOR UPDATE`): accounts are locked in id order, and positions and orders by key.
  - Serializable would make concurrent requests fail with serialization errors, and every caller would need a retry loop.

## Database
- **Migrations:** embedded, applied in name order in one transaction under an advisory lock, and recorded in `schema_migrations`.
- **Seed:** the seed data lives in the first migration: user 1 and the five ledger accounts.
- **Tests:** each test gets its own schema (`t_<random>`) in `tradeapp_test`, migrated from scratch and dropped afterwards. This lets packages run in parallel against one database.
- **Order and quote tables:** these exist from phase 1 so the invariants can be checked from day one.
- **IDs:** prefixed ULIDs from `pkg/lid`, generated by the service: `order-01JC3V…` for orders, `fund-01JC3V…` for fundings. ULIDs are time-ordered, so ids sort by creation. The id columns are `TEXT`, and the repo inserts the id it is given. The prefix is `order`, not `ord`, so our ids aren't confused with brokersim's own `ord_…` ids. `pkg/lid` holds only the prefixes this app uses.
- **Belt and braces:**
  - `accounts` has `CHECK (owner_id IS NULL OR balance >= 0)` on top of the check in the service.
  - `positions` has checks that quantities stay non-negative and `held_qty <= qty`.

## Ledger (service/ledger.go)
- **How `postEntry` works:**
  1. Validates the entry.
  2. Claims `(kind, source_type, source_id)`. A duplicate means it's already posted, so it returns `false` and changes nothing.
  3. Locks the accounts it touches in id order.
  4. Refuses to take any user account below zero (`ErrInsufficientFunds`).
  5. Writes the postings and the new cached balances.
- **Source ids:**
  - **Funding:** a fresh `fund-<ULID>` from the service, so each `FundAccount` call is a separate credit. Retry safety comes from the transport's idempotency keys.
  - **Holds and releases:** keyed by order id, so an order is released at most once. Releasing 0 posts nothing.
  - **Fills:** keyed by provider fill id.
- **BuyFill and fees:**
  - `payBuyFill` takes `fromHeld` from the caller. Anything above it (fee rounding, or a fill after the hold is used up) comes from available cash.
  - If available cash is also short, it returns `ErrInsufficientFunds`. Phase 3 turns that into a recon break, so the fill is still recorded.
- **Fee posting:** a fill's fee is part of the fill's own journal entry.

## Positions
- **Average cost:** `(qty*avg + q*p) / (qty + q)` with integer division, which rounds down. Buy fees are not in the average cost.
- **Realized P&L on a sell:** `(p - avg) * q - fee`. The average cost is unchanged, and selling to zero resets it to 0.
- **Duplicate fills:** every fill writes a `position_movements` row keyed by `fill_id`, so a duplicate fill moves the position once.
- **Overselling:** a sell fill larger than the position is refused with `ErrInsufficientShares`. Phase 3 decides how that becomes a break.

## Idempotency (transport middleware on POST routes)
- **How a request runs:**
  1. Reserve the key in its own short transaction.
  2. Run the handler, capturing its response.
  3. On 2xx, store the status and body. On any other status, delete the key so the client can fix the cause and retry with the same key.
- **Same key again:**
  - Different request (method, path and raw body hash) → `422 idempotency_conflict`.
  - Still running → `409 request_in_progress`. With 20 concurrent same-key requests, one does the work and the others get `409` or a replay.
  - Finished → replay the stored status and body byte for byte, with `Idempotent-Replayed: true`.
- **Crashes:** if the process dies after the work commits but before the response is stored, the key stays "in progress" (`409`) until it expires. The work is never repeated.
- **Saving the result:** uses a context that survives the client disconnecting.
- **Expiry:** keys older than `IDEMPOTENCY_TTL` (24h) are deleted hourly by `httpapi.Server.RunKeyCleanup`. It stays in the transport layer with the rest of idempotency, rather than going on the job system.

## API
- **Errors:** JSON as `{"error": {"code", "message"}}`.
- **Strict request bodies:** unknown fields, trailing data and non-integer amounts are rejected with `400 validation_error`.
- **Funding:** `POST /api/account/fund` requires `Idempotency-Key` (max 255 characters) and an amount from 1 to 10,000,000 minor units. It returns `200 {amount, cash}`.
- **Account summary:** `GET /api/account` values each position at the provider's current **bid** (what selling now would fetch, before fees): `last_price`, `market_value`, `unrealized_pnl = (bid − avg_cost) × qty`. If prices can't be fetched, those fields are `null` and the rest of the account still loads.
- **Prices:** `GET /api/prices` proxies brokersim with a 1s cache in the service.
- **Quotes:** `POST /api/quotes {symbol, side, qty}` validates locally (symbol `A-Z0-9`, at most 16 characters; side `BUY|SELL`; qty from 1 to 1,000,000), asks brokersim, and stores the quote. Brokersim `400/404` → `400 validation_error`. Brokersim unreachable or `5xx` → `502 provider_unavailable`. Not idempotent: every call is a new quote.
- **Placing orders:** `POST /api/orders {quote_id}` requires `Idempotency-Key` and returns `201` with the order in `PENDING_SUBMIT`.
  - Unknown quote → `404`.
  - Expired quote (checked locally) → `409 quote_expired`.
  - Quote already used → `409 quote_already_used`.
  - Not enough cash or shares → `422`.
- **Listing orders:** `GET /api/orders?status=open|all` returns up to 200 orders, newest first. The default is `all`. `open` means not final.
- **One order:** `GET /api/orders/{id}` returns the order with its fills and activity. A malformed or unknown id → `404`.
- **Admin:** `GET /api/admin/jobs?status=dead|pending|running|done` (default `dead`) and `POST /api/admin/jobs/{id}/retry`. Only dead jobs can be retried; anything else → `409 conflict`.
- **Activity:** `GET /api/activity?after=<id>&limit=<n>` lists items oldest first. The default limit is 100, the maximum 500.

## Invariants
- **Checks** (each one a plain `InvariantRepo` method that returns problem lines):
  - Every entry balances, and all balances sum to 0.
  - Each cached balance equals the sum of its postings.
  - No user balance is negative.
  - `cash_held` equals the holds on non-final BUY orders.
  - `held_qty` equals the holds on non-final SELL orders.
  - No position is negative.
  - Each position's quantity equals the sum of its movements.
- **`Service.CheckInvariants`** runs them all and caps each result's detail at 10 lines.
- **Tests:** `dbtest.AssertInvariants` runs them at the end of every test.

## Provider client (`internal/provider`)
- **Plain HTTP gateway.** Each brokersim call is one method: `CreateQuote`, `AcceptQuote`, `GetOrder`, `GetOrderByClientOrderID`, `ListPrices`. Every request sends `X-Api-Key`.
- **Errors:**
  - Any non-2xx answer becomes `*provider.APIError{Status, Code, Message}`.
  - Network errors and timeouts (`PROVIDER_TIMEOUT`, default 5s) are returned as they are.
  - The client doesn't interpret either; the service decides what an answer means.
- **Accept** sends our order id both as `client_order_id` and as `Idempotency-Key`. Brokersim answers a repeat of the same quote and id with the same order.

## Placing an order
- **One transaction** (`PlaceOrder`):
  1. Load the quote and check it hasn't expired.
  2. Create the order as `PENDING_SUBMIT`. `orders.quote_id` is unique, so a second order for the same quote fails with `quote_already_used`.
  3. Hold the quote total in cash (BUY) or the quantity in shares (SELL).
  4. Queue a `submit_order` job.
  5. Add an activity item.
- **After commit:** the worker is nudged so it doesn't wait for the next poll.
- **Order id:** `order-<ULID>`, generated by the service. It is also the brokersim `client_order_id`, which accepts any non-empty string. A malformed id (`lid.Validate` fails) is treated as not found (`404`).

## Jobs, retries and the dead-letter queue
- **The `jobs` table is the outbox:**
  - `status`: `pending` → `running` → `done`, or `dead`.
  - Other columns: `attempts`, `max_attempts`, `run_at`, `locked_until` (the lease) and `last_error`.
- **Claiming** (`ClaimJobs`) runs in one transaction:
  - It locks due jobs with `FOR UPDATE SKIP LOCKED`, so many workers never get the same job.
  - Due means `pending` with `run_at <= now`, or `running` with an expired lease (its worker died).
  - Each claimed job becomes `running`, gets `attempts + 1` and a lease of `JOB_LEASE` (30s).
- **Running** (`RunJob`): the job runs outside any transaction, because it makes HTTP calls. Then:
  - Success → `done`.
  - Permanent error (e.g. a job with nothing to work on) → `dead` straight away.
  - The circuit was open, so brokersim was never called → **deferred**: back to `pending`, due in `JOB_BACKOFF_BASE`, and the attempt is handed back. The retry budget still runs.
  - Any other failure → back to `pending` after the retry delay, or `dead` once the job is out of retries (`domain.Job.OutOfRetries`).
  - If our lease expired and another worker reclaimed the job, our late result is ignored: the attempt counter no longer matches.
- **Retry budget, not just a retry count:**
  - Every job gets `give_up_at = created + JOB_RETRY_BUDGET` (15m) and keeps retrying until then.
  - The last retry is scheduled exactly at `give_up_at`; only if that fails does the job go `dead`.
  - `JOB_MAX_ATTEMPTS` (50) stays as a hard safety cap.
  - Why: the old rule (6 attempts from 1s) gave up after about 31 seconds, so a one-minute brokersim outage would have sent every in-flight job to the DLQ. A budget says how long we're willing to wait for brokersim, whatever the attempt count.
  - Retrying from the DLQ (or the sweeper re-queuing a dead cancel) gives the job a fresh budget.
- **Full jitter:** the retry delay is a random point between `JOB_BACKOFF_BASE` (1s) and that attempt's ceiling, `base × 2^(attempt−1)` capped at `JOB_BACKOFF_MAX` (2m). After an outage, jobs that failed together retry spread across the whole window instead of in a burst. The floor of `base` means a retry never fires instantly.
- **Retrying from the DLQ:** `RetryJob` turns a dead job back into `pending` with 0 attempts, due now.
- **The worker** (`internal/worker`) only loops and calls the service. It wakes every `WORKER_POLL` (1s), or as soon as an order is placed. The API runs one worker.
- **Periodic tasks:** the worker also runs the sweeper (`SWEEP_INTERVAL`) and reconciliation (`RECON_INTERVAL`). Idempotency-key cleanup runs in transport (`RunKeyCleanup`).

## Submitting to the provider (the `submit_order` job)
- **Already resolved:** if the order is no longer `PENDING_SUBMIT` (accepted, rejected, or cancelled locally), the job is done.
- **Retries check first:** on attempt 2 and later, `GET /v1/orders?client_order_id=` comes before accepting again. If brokersim already has the order (an accept whose answer was lost), we adopt it. A `404` means accept for real.
- **Outcomes:**
  - Accept succeeds → store `provider_order_id` and move `PENDING_SUBMIT` → `OPEN`.
  - A definite refusal (`400`, `404`, `409`, `422`, e.g. `quote_expired`, `market_closed`, `quote_already_accepted`) → `REJECTED` with the brokersim code as the reason, and the hold is released in the same transaction. The job is done: a rejection is an answer.
  - Anything else (`5xx`, `401`, timeout, network) → outcome unknown, so retry with backoff, then the DLQ. The order stays `PENDING_SUBMIT` with its hold until a retry succeeds or the sweeper (phase 3) resolves it.
- **No `provider_version` yet:** `provider_order_id` is stored, but the version isn't. Phase 3's webhook processor applies brokersim's snapshots by version, so the first `order.accepted` (version 1) still applies.

## Testing against the provider
- **`internal/providertest`** is an in-process fake of brokersim's `/v1` API: quotes, accept, order lookups and prices. Its scripted modes are:
  - accept OK;
  - `500` with nothing created;
  - `500` after creating the order (the ambiguous accept);
  - `409 quote_expired` / `market_closed`;
  - fully down (`503`).
- **Clock:** the service has a replaceable clock (`now`), so tests move time forward to make retries due instead of sleeping.
- **Manual smoke test** against the real brokersim (with `SIM_AUTO_FILL=false`): a placed order reaches `OPEN` and brokersim holds it under our id as `client_order_id`. With the market closed it becomes `REJECTED` (`market_closed`) and the cash is released.

## Webhooks in → inbox → processor (phase 3)
- **Endpoint:** `POST /webhooks/provider` (no `Idempotency-Key`; the event id dedupes).
  1. Reads the raw body (1 MB max).
  2. Checks `X-Sim-Signature` = hex(HMAC-SHA512(secret, `ts + "." + body`)) with a constant-time compare. `X-Sim-Timestamp` must be within `WEBHOOK_TOLERANCE` (5m) of now, in either direction. Anything else → `401`, and nothing is stored.
  3. Stores the event in `provider_events` and queues a `process_event` job, in one transaction. A duplicate event id → `200`, and nothing new is queued.
  4. Answers `200` straight away; processing happens in the worker. A valid signature on an unparseable body → `400`.
- **The `process_event` job:** applies one event to its order in one transaction, then marks the event processed.
  - **Finding the order:** by `provider_order_id`, or by `client_order_id` (our order id) when the event arrives before the accept answer.
  - **Unknown orders:** processed with `process_error = 'unknown_order'`. That's a note, not a failure.
  - **Events without an order** (`quote.expired`): marked processed and otherwise ignored.

## Applying a provider snapshot (`service/snapshot.go`)
- **One code path for webhooks, cancel answers and the sweeper,** so they can't disagree. `applySnapshot(order, snapshot, fills)` on a locked order:
  1. Stores `provider_order_id` if it's missing.
  2. **Fills** are applied by `fill_id` (unique in `order_fills`), whatever the order of arrival. Each fill:
     - writes the fill row;
     - pays the BUY from the hold first, then from available cash, or credits the SELL net of its fee;
     - moves the position;
     - lowers `hold_remaining`.
  3. **Status, `filled_qty`, `avg_fill_price`** come only from a snapshot whose `version` is newer than `orders.provider_version`. `domain.NextStatus` picks the status.
  4. **A final order releases** whatever it still holds, in the same transaction.
- **`domain.NextStatus` rules:**
  - A final local status never changes: the first final state wins.
  - While we're `PENDING_CANCEL`, a snapshot that says `OPEN` or `PARTIALLY_FILLED` keeps `PENDING_CANCEL`. That snapshot is a fill made before the broker saw our cancel. The exception is `order.cancel_rejected`, which takes the provider's status.
  - Otherwise we take the provider's status.
- **Version bookkeeping:**
  - Brokersim's too-late `cancel_rejected` doesn't bump the version, so it changes nothing.
  - `provider_version` starts at 0, because the submit job doesn't record a version. Brokersim's first `order.accepted` (version 1) therefore still applies.
- **Order of release vs fills:** if `FILLED` (newer) is applied before an older fill arrives, the hold is released first and the older fill then pays from available cash. The end result is the same money.

## Fills that don't fit: breaks, never errors
- **Rule:** a fill is a fact. It's always recorded, and a contradiction is written to `breaks` (exposed by `GET /api/breaks`) instead of failing the event.
- **Break kinds:**
  - `fill_after_final`: the fills recorded on a final order now add up to more than its final `filled_qty` (a real late fill). An older fill arriving after a newer final snapshot does **not** count: it's within `filled_qty`.
  - `fill_unpaid`: a BUY fill that the hold plus available cash can't cover. The fill row and the shares are recorded, but no money moves. We check before posting, because a refused posting would abort the transaction.
  - `fill_shares_missing`: a SELL fill for shares we don't hold. The fill row is recorded; no shares or cash move.
  - `submit_never_accepted`: see the sweeper.

## Cancel (`DELETE /api/orders/{id}`)
- **`PENDING_SUBMIT`, submit job still pending:**
  - The job row is locked, so the worker can't claim it meanwhile. The job is marked done and the order cancelled locally, with the hold released.
  - Answers `200`, and the order is never sent.
  - If the submit job is already running or dead → `409 conflict`, because the order may be at the broker. Try again shortly; the sweeper settles dead ones.
- **`OPEN` / `PARTIALLY_FILLED`:** the order moves to `PENDING_CANCEL` and a `cancel_order` job is queued. Answers `202`. **Nothing is released on the request,** only on the final state.
- **Already `PENDING_CANCEL`:** `202`, with no new job.
- **Final:** `409 order_final`.
- **The `cancel_order` job:**
  - Calls `DELETE /v1/orders/{id}` and applies the snapshot that comes back, with all its fills.
  - On `409 order_final`, it fetches the order and applies that.
  - On `5xx` or a timeout, it retries with backoff and then goes to the dead-letter queue. On `404` (the provider has no such order), it fails permanently.
  - The final outcome normally arrives as a webhook.

## Stuck-order sweeper
- **Schedule:** every `SWEEP_INTERVAL` (15s) the worker checks up to 50 active orders that haven't changed for `STUCK_AFTER` (30s), oldest first.
- **Each order:** `GET /v1/orders/{id}` (or by `client_order_id`), then the result is applied through `applySnapshot` with all the provider's fills, and the order's `updated_at` is touched. One order failing doesn't stop the others.
- **`PENDING_SUBMIT` orders:**
  - Left alone while their submit job is pending or running.
  - Once the job is dead: if brokersim has the order, adopt it. If it doesn't and the quote has expired (no retry could ever succeed), reject the order as `submit_failed`, release the hold and record `submit_never_accepted`. If the quote is still valid, wait: a manual job retry can still work.
- **Dead cancels:** after polling a `PENDING_CANCEL` order, if it's still `PENDING_CANCEL` and its `cancel_order` job is dead (the provider was unreachable for every attempt), the sweeper re-queues that job with fresh attempts.

## Activity and outcome lines
- **Activity items** are written for: placed, submitted, every fill ("Bought 4 AAPL at $190.12 (fee $0.95)"), status changes, cancel requested, and the hold returned.
- **`domain.OutcomeLine`** gives the final result in words:
  - "Filled"
  - "6 of 10 bought, 4 cancelled"
  - "Expired: 3 of 10 bought"
  - "Rejected: quote_expired"
- **`GET /api/admin/invariants`** runs the books checks and returns `{ok, invariants}`.

## Testing phase 3
- **The fake broker** (`providertest`) also changes orders the way brokersim's engine or `/dev` API would: `Fill`, `ConfirmCancel`, `RejectCancel`, `Expire`, `Reject`. Each returns the webhook event brokersim would send, so tests can deliver it, deliver it twice, deliver it out of order, or drop it.
- **Mutation checks:** turning off the version guard, or the `PENDING_CANCEL` rule, makes a test fail (`TestOlderSnapshotDoesNotRewind`, `TestFillFromBeforeTheCancelKeepsPendingCancel`).
- **End to end against the real brokersim** (auto-fill on, real signed webhooks): 5 buys, a cancel mid-fill and a sell all reach the right final state. Invariants OK, no breaks, empty dead-letter queue.
  - With brokersim's webhook URL pointed at a dead port, all 50 webhooks failed to deliver, and the sweeper alone brought every order to the same correct end state.
- **Brokersim IDs are seeded** (`SIM_SEED`, default 42), so a restarted brokersim reissues the same quote and order ids. Against a trade database that kept its data, the quote insert then fails on a duplicate id. Run brokersim with a fresh `SIM_SEED`, or reset the trade database, between brokersim restarts. A real provider's ids are globally unique.

## Reconciliation (phase 4)
- **When:** every `RECON_INTERVAL` (5m) in the worker, and on demand with `POST /api/recon/run`. `GET /api/recon/latest` returns the last stored report.
- **Each run:**
  1. Fetches the provider's orders changed in the last `RECON_LOOKBACK` (24h) with `GET /v1/orders?since=`.
  2. Loads ours changed in the same window.
  3. Compares each order with `domain.CompareOrder`, a pure, unit-tested function, and records:
     - `status`, if the local and provider statuses differ;
     - `filled_qty`, if the filled quantities differ;
     - `fill_missing_local`, for a fill the provider has and we don't;
     - `fill_unknown`, for a fill we have and the provider doesn't.
  4. Also records orders found on one side only:
     - `missing_at_provider`: we have a provider id, but the provider has no such order.
     - `unknown_to_us`: the provider has an order whose `client_order_id` isn't one of ours. Before flagging it, the run checks the whole orders table, not just the window.
  5. Runs every invariant and counts the open breaks.
- **Settling window:** an order that changed on either side within `STUCK_AFTER` is counted as `orders_skipped`, not compared, because a webhook may still be in flight. The run would otherwise report noise.
- **Never-sent orders** (refused at submit, or cancelled before sending) have no provider id and aren't expected at the provider.
- **`ok`** means no mismatches and every invariant holds.
- **Storage:** reports are stored whole as JSON in `recon_runs`. Run ids come from the service (`recon-<ULID>`), so the repo write returns only an error.
- **Mismatches aren't written to `breaks`.** Breaks are contradictions found while processing events. A mismatch that persists would otherwise be re-recorded on every run.
- **Restarted brokersim:** brokersim is in memory, so after a restart its orders are gone and our recent orders show up as `missing_at_provider`. That is expected in development.

## Comparing one order (`GET /api/orders/{id}/compare`)
- **Response:** our order and fills next to the provider's live snapshot (`GET /v1/orders/{id}`, or by `client_order_id` if we have no provider id), plus the same mismatch list and `agree`.
- **No settling window:** it shows exactly what each side says right now.
- **An order never sent** isn't known to the provider. That's expected, and the response has `provider: null` and `agree: true`.
- **Provider unreachable** → `502`.

## Order ids in requests
- **Normalisation:** every order id that comes in (paths, webhook `client_order_id`) goes through `lid.Normalize`, giving a lower-case prefix and an upper-case ULID. `ORDER-01jc…` finds `order-01JC…`. Ids we create are already canonical.

## End-to-end tests (`make e2e`, `make e2e-dropped`)
- **Script:** `scripts/e2e.sh`.
  1. Builds both binaries.
  2. Runs them on their own ports (API 18091, brokersim 18090) and their own database (`tradeapp_e2e`, recreated every run), so the dev setup is untouched.
  3. Gives brokersim a fresh `SIM_SEED`.
- **Scenario:** 5 buys, one cancelled mid-flight, then a sell. It waits until every order is final (60s limit) and settled, then runs reconciliation.
- **Assertions:**
  - The sell filled.
  - Invariants OK, no breaks, no dead jobs, no cash held.
  - Recon OK, with at least 7 orders checked.
  - The cancelled order agrees with the broker.
  - No `ERROR` lines in the API log.
- **`make e2e-dropped`** points brokersim's webhooks at a dead port, so the sweeper alone has to bring every order to the same result.

## Circuit breaker on brokersim calls (`internal/provider/breaker.go`)
- **Inside the provider client,** so every brokersim call goes through it: jobs, the sweeper, reconciliation, quotes and prices.
- **States:**
  - `closed`: calls go through. `BREAKER_THRESHOLD` (5) failures in a row open the circuit.
  - `open`: calls fail at once with `ErrCircuitOpen`, without touching the network, for `BREAKER_COOLDOWN` (15s).
  - `half_open`: one test call goes through. Success closes the circuit; failure opens it for another cooldown.
- **What counts as a failure:** only signs that brokersim itself is in trouble (network errors, timeouts, `5xx`, `429`). A `4xx` is a real answer from a working brokersim, so it counts as a success. If *our* context is cancelled, the call is abandoned and frees the test slot without judging brokersim.
- **While open:**
  - The worker only claims jobs that don't need brokersim (`process_event`), so webhook processing continues.
  - Provider jobs wait in the queue without using attempts. The few claimed just before the circuit opened are deferred, as above.
  - API calls that need brokersim (quotes) fail fast with `502`.
- **Logging:** every state change is logged (`WARN` on open, `INFO` on half-open and close). Deferred jobs are logged at `INFO`, not as failures.
- **One breaker per process.** With several API instances, each learns brokersim's health on its own, which is fine for this design.
- **Verified with a real outage:** brokersim was frozen with `SIGSTOP`, so calls timed out. Three failures opened the circuit, two jobs were deferred without using attempts, and quote requests failed fast. A test call made while brokersim was still frozen re-opened the circuit; after `SIGCONT` the next test call closed it, and all 5 orders went `OPEN`, with nothing in the DLQ.

## Job queue visibility and alerting
- **`GET /api/admin/jobs/stats`** returns:
  - job counts by kind and status;
  - pending, running and dead totals;
  - `oldest_waiting_seconds`: the age of the oldest pending or running job (queue lag);
  - the provider circuit state;
  - `alerts` and `ok`.
- **Alerts** (the rules are in `domain.JobAlerts`, unit-tested):
  - `dead_letter_queue_not_empty`: a job gave up and needs a human.
  - `queue_lag`: a job has waited longer than `JOB_LAG_ALERT` (5m).
  - `provider_circuit_open`: brokersim calls are paused.
- **Dead-letter log:** every dead-lettered job logs `WARN job dead-lettered` with its id, kind, attempts, order id and error. This is the line to alert on in a log system.
- **Paging:** in production a monitor would poll the stats endpoint (or scrape the same numbers as metrics) and page on any alert. Wiring up a pager is out of scope here.
- **`RunJob`** returns the job's status afterwards, so the worker can tell a dead-letter from an ordinary retry.

## Bulk replay of the dead-letter queue
- **`POST /api/admin/jobs/retry`** replays dead jobs in bulk, each with a fresh retry budget.
  - Optional JSON filters: `kind` (only that job kind) and `from` / `to` (RFC 3339; jobs that died in that window).
  - An empty body replays every dead job.
  - Up to 1000 jobs per call; returns `{retried: n}`.
- **Use after an incident:** once the cause is fixed, replay everything from the incident window in one step instead of job by job.
- **Why it's safe:** every job can run twice without harm. A retried submit reuses the same `client_order_id` and checks first whether brokersim already has the order. Fills are deduped by id, and status changes are guarded by version.
- **Validation:** an unknown kind, or `from` not before `to`, → `400`.

## Live updates (SSE)
- **`GET /api/stream`** streams Server-Sent Events of the durable activity feed.
  - It replays everything after `?after=<id>`, or after the `Last-Event-ID` a browser sends on reconnect, then follows new items. Each event's id is the activity id, so a reconnect resumes exactly where it left off.
  - It polls the `activity` table every 500ms rather than using in-memory pub/sub, so nothing is missed and it works with several API instances.
  - A heartbeat comment every 15s keeps the connection open.
  - The stream lifts the server's write timeout for its own connection.
- **Middleware fix:** `statusWriter` has `Unwrap()`, so `http.ResponseController` can flush and set deadlines through the logging middleware.

## Webhook security: signature, timestamp, nonce, replay
- **Every webhook must pass, in order:**
  1. **Timestamp** within ±`WEBHOOK_TOLERANCE` (5m) of now. Otherwise `401`.
  2. **Nonce** present and at most 64 characters. Otherwise `401`.
  3. **Signature:** `hex(HMAC-SHA512(secret, "<ts>.<nonce>.<body>"))`, compared in constant time. Otherwise `401`.
  4. **Replay check:** the nonce is inserted into `webhook_nonces`. If it's already there, the request is a replay → `409 replay_detected`, and nothing is stored or processed.
  5. **Event id dedupe** (the inbox): an already-received event id → `200`, ignored.
- **Why both a nonce and the event id:** the nonce stops an attacker re-sending a captured request within the 5-minute window. The event id stops the provider's own legitimate retries (each with a new nonce) from being applied twice. Between them, a request can neither be replayed nor applied twice.
- **Nonce cleanup:** nonces are kept for twice the tolerance, then deleted (`RunKeyCleanup`). Anything older is already refused by the timestamp check.
- **Status codes:** a refused request never reaches the inbox. `401` means "not from the provider"; `409` means "the same request again".

## Webhook log and inspector
- **`webhook_log`** records every request, whatever its outcome: `accepted`, `duplicate`, `rejected_signature`, `rejected_timestamp`, `rejected_nonce`, `rejected_replay`, `invalid_body` or `error`.
  - It also keeps the signed headers. Only the first 16 characters of the signature are stored, never the whole value.
  - It keeps the remote address and the body (up to 64 KB). For refused requests the body is unverified; it's kept for debugging and never processed.
  - Rows are deleted after 7 days.
- **Endpoints:** `GET /api/admin/webhooks` (recent entries, oldest first), `GET /api/admin/webhooks/stream` (live SSE, sharing the `sse` helper with the activity stream) and `GET /api/admin/webhooks/{id}` (one entry with its body and processing state from the inbox).
- **Layering:** the log is about HTTP requests, so the transport layer writes and reads it directly through `WebhookRepo`, as it does for idempotency.
- **Structured logs** (slog): `webhook received` / `webhook refused` (outcome, event id, type, nonce, remote address), plus, from the service (`Config.Logger`): `webhook stored`, `webhook duplicate ignored`, `event applied` (type, order, status, version, fill), `event for an unknown order`, `order placed`, `order submitted`, `order rejected by provider`, `cancel requested` and `break recorded`.
